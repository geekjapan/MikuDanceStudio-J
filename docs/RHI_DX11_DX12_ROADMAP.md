## 2. 把“接入完成”分成可验收的交付

1. **A：DX11 可用预览。** 应用可主动选择 DX11；在已声明支持的单采样、无 MME
   场景中完成加载、跳帧、播放、编辑和呈现。遇到不支持的场景在执行前明确阻断或
   按已选择的回退政策返回 DX9。它不叫完整渲染器。
2. **B：DX11 原生功能覆盖。** PMD/PMX、多模型、饰品、描边、地面、投影阴影、
   内置自阴影、背景、选择辅助、HUD／文字、目标缩放、截图和录制等已盘点的绘制
   均能在该后端执行。规定范围的抗锯齿和多 GPU 验收通过。
3. **C：DX12 原生功能覆盖。** 使用同一场景／材质／通道输入达到 B 的功能范围；
   同时通过 DX12 的描述符、屏障、在途资源和 fence 生命周期验证。
4. **D：效果兼容。** 明确支持哪些遗留 MME FX 功能和哪些效果样例；DX11/DX12
   对该兼容范围完成验证。不能把任意第三方效果的兼容性包含在 B/C 的声明中。

IK 和物理暂时由旧 CPU 运行时求解。RHI 消费同一份最终姿态和变形顶点，
不要求先重写求解器，也不在这条计划中引入 GPU 蒙皮。
Windows 窗口和编辑 UI 可以保留；窗口跨平台迁移是另一条任务。

## 3. 共用边界：为两个后端准备真正可提交的帧

沿用 [RHI 接口契约](RHI_INTERFACE_CONTRACT.md) 的职责分离，但优先实现项目实际
需要的子集。借鉴 Unity 的设备、资源和提交边界，不复制其整套类层级。

| 边界 | 建议交付 | 关键约束 |
| --- | --- | --- |
| 帧数据生产者 | CPU 拥有的 FrameRenderData，包含最终网格、材质、视口、通道和顺序 | 没有 IDirect3D、D3DX 或后端纹理指针 |
| 资源登记 | 命名空间 + 资源 ID + 版本 + 描述符／内容校验 | 同一版本不能对应不同字节；删除和模型卸载有明确事件 |
| GPU 缓存 | 设备身份下的纹理、静态索引、动态网格、管线缓存 | 缩放仅作废目标相关内容；设备替换重新上传 |
| 通道 | 颜色／深度／模板附件、尺寸、采样数、load/store/clear/resolve | 自阴影写入后采样必须声明依赖 |
| 编码和提交 | Encoder / FinishedCommands / GraphicsQueue / CompletionFence | 单次提交、资源在途存活、设备和目标世代检查 |
| 着色包 | 顶点布局、常量布局、绑定布局、各 API 编译变体 | 记录编译器／选项；double 是明确能力要求 |
| 恢复协调 | 暂停、等待或丢弃在途任务、重建目标／设备、恢复资源 | 不复用旧 fence、旧描述符或旧提交 |

CPU 不可变数据与本机 GPU 资源分开保存。设备 epoch 校验不能替代 GPU 完成 fence：
前者拒绝旧提交，后者决定上传内存、描述符和 command allocator 何时可以重用。
目标缩放时不得把全部纹理缓存清空。

第一版只需要一个 graphics queue、有限数量在途帧、后端自动生成资源转换。
异步 compute、多队列、多线程录制、通用复杂 FrameGraph 和 bindless 不作为首次接入前提。

## 4. DX11 工作包与通过条件

### P0：建立全功能台账

逐项盘点 `frame_scene.cpp`、`model_renderers.cpp`、`accessory.cpp`、
`overlay_producers.cpp`、`frame_driver.cpp`、`device_reset.cpp` 和录制／回读入口。
为每项记录输入、资源、目标、顺序、所需能力、测试和不支持时的处理。
将“内置效果”与第三方 MME 效果区分，列出真正尚未通过的素材和状态组合。

通过条件：每个实际绘制／目标切换都有归属；不能无声省略未支持的绘制。
交付 `RenderFeatureSupport` 台账及一组合法可分发的生成素材。

### P1：常驻资源与场景提交缓存——主要生命周期已实现

把重放拆成资源准备、目标准备、常量／动态几何更新、编码、提交和可选回读。
资源 ID 在不同帧和场景之间不能意外别名；静态索引、纹理只在版本变化时上传。
动态顶点更新采用有容量和帧生命周期的缓冲策略；管线／采样器按描述缓存。
旧版本释放遵守 backend 完成条件，不让播放过程累积无限历史版本。

通过条件：1000 个不变帧没有重复静态上传；一次纹理／网格编辑只更新对应资源；
卸载回到稳定资源数量；连续缩放和设备替换保留正确的身份、版本及图像。
报告静态上传次数、动态字节量、CPU/GPU 帧耗时和内存峰值。

### P2：实时生产者脱离 DX9 对象——CPU 几何桥接已实现

当前实现与验收范围见 [RHI_CPU_GEOMETRY.md](RHI_CPU_GEOMETRY.md)。模型加载与
蒙皮直接拥有 CPU 几何，已接共用 SceneRenderer；诊断批次不读回 DX9 网格。
CPU 着色输入已接默认关闭的独立批次诊断，接口与验收见
[RHI_CPU_MODEL_INPUTS.md](RHI_CPU_MODEL_INPUTS.md)。2026-10-06 已完成真实 PMM 材质 13 的
x64/x86 字段审计及直接 CPU 输入诊断，DX11/DX12 离屏图像和目标／设备恢复均通过。
直接模式按构建和素材的审计结果准入。完整绘制顺序、独立应用呈现尚待迁移，P2 尚未整体完成。
有序多材质 CPU 提交已实现，首组为独立材质 12、13、14；
模型生产者、纹理版本、原生控制测试及最终构建复验限制见
[RHI_CPU_MULTIMATERIAL.md](RHI_CPU_MULTIMATERIAL.md)。

从旧模型求解／蒙皮结果直接生产 CPU 变形顶点，接入相机、灯光、材质、饰品绑定、
显示顺序和编辑变化。DX9 与 DX11 消费同一份最终数据。
保留旧 IK／物理时序，不在测试中靠反复读回 DX9 顶点缓冲驱动 DX11。
独立于后端的资源加载先完成 CPU 部分，再由选定后端创建 GPU 对象。

通过条件：DX11 预览无需一个“负责实际渲染的 DX9 设备”；
首次加载、跳帧、顺序播放、骨骼／Morph／材质编辑和模型卸载有一致输入记录。
确定性图像对照先冻结物理结果并复用；连续物理播放另测时序，不混淆随机／状态差异。

### P3：通道与完整基础画面

先保留已通过的地面、饰品、投影阴影、模型材质输入；随后补描边、
背景图片／视频、选择辅助线／标记、HUD 和文字。
再将多目标通道接入，完成内置自阴影贴图写入、目标切换、采样和合成。
支持实际透明绘制顺序、深度写开关和模板行为，不用粗略重新排序改变画面。

通过条件：每个家族有生成控制用例和实际场景对照；全帧包含前后顺序和遮挡历史。
描边、地面投影阴影和自阴影分别验收。
Windows 可以继续提供 GDI 字形 RGBA，DX11 消费图集；可移植字体替换是独立选择，
不能为了后端迁移悄悄改变已有文字外观。

### P4：接入应用与输出——达到 A

增加集中后端配置、支持范围提示和诊断旁路，默认 DX9。
先由应用内单采样对照同时验证相同帧，再开放 DX11 完整帧呈现。
整帧选择一个后端；涉及未支持 MME 场景时执行前处理，不能缺一部分效果仍宣称成功。
运行中后端切换在安全帧边界暂停、退出旧资源、创建新设备后恢复场景。
截图和 AVI／图像序列等输出改走统一回读数据，保留格式、色序、步长、尺寸和时序。

通过条件：真实 v1/v2 PMM 在 x64/x86 完成资源重选、跳帧、播放、编辑、Save As／回读、
连续缩放、最小化恢复、重复切换和资源恢复。
相同冻结帧的比较继续零差异；诊断回读不进入正常每帧路径。

### P5：MSAA、驱动与功能矩阵——达到 B

实现采样数、质量模式和实际 resolve 通道；交换链与 MSAA 场景目标分离。
逐步验收 2×／4×／8×：遮挡、模板、半透明、AlphaTest、描边和自阴影均单列。
DX9 无法完整取得逐样本历史时使用完整前序重放，不能用解析色替代深度／模板历史。

当前“与 DX9 零差异”的要求继续保留。不同 API／GPU 的采样位置和固定功能运算
可能无法完全一致；失败明确报告，阻断相应能力的完成声明。
不以增大像素容差、无声关闭 MSAA 或不断拟合少数像素代替验收。
先让单采样预览推进，MSAA 未通过则仍是公开未完成项。

通过条件：建立至少两个独立硬件族及 WARP 的适用矩阵，失败／不可用／通过分开；
完成明确支持范围的整帧回归、稳定播放和设备恢复验证。

### P6：持续验收与发布整理（与 P1–P5 并行）

普通 CI 保留 Windows/Linux/macOS 的资源、版本、通道和提交契约测试。
Windows 图形 CI 同时有生成用例和可合法入库的小场景；自建 GPU 节点覆盖真实显卡。
私有 PMM 用外部测试运行，GPU 不可用或缺素材的跳过不计通过。
版本记录包括驱动、适配器、采样模式、兼容策略和着色器编译选项。

交付功能矩阵、用户后端选择说明、诊断导出、性能记录和回退流程。

## 5. DX12 工作包与通过条件

DX12 已接入 P1 的共用资源版本和提交层，单目标 Q1/Q2/Q3 主流程已经实现。
下列条件仍保留为完整范围的验收清单；上传池、描述符耗尽恢复、编译反射、多通道和
应用主窗口尚未全部完成，不能将单采样的当前结果扩展为全功能通过。

### Q1：设备、交换链和完成同步——单采样实现并验证

创建 device、graphics queue、command allocator/list、fence、帧上下文和
flip-model swapchain；执行 clear / present / 连续 resize / minimize / restore。
后台缓冲帧 token、当前索引、present 状态和 resize 释放顺序明确。
MSAA 是中间目标，不是直接给 flip swapchain 配置多采样。

通过条件：空帧呈现、重复缩放／设备替换、旧提交拒绝和 debug layer 检查通过；
allocator 仅在其完成 fence 后重用。

### Q2：资源、上传和描述符——基础实现并验证，池化继续推进

实现 default/upload/readback heaps、对齐和 texture footprint、缓冲／Mip 上传、
SRV/CBV/sampler/RTV/DSV 描述符、受 fence 保护的上传环和延迟销毁。
静态资源复用 P1 CPU 登记；动态几何和常量不会覆盖在途帧仍在读取的数据。
double shader 能力查询和显式不支持原因沿用兼容政策。

通过条件：多帧更改纹理／顶点、卸载、描述符耗尽恢复、设备重建有独立生命周期测试；
所有旧资源和旧设备命令被拒绝，未完成提交的资源不能过早释放。

### Q3：管线、绑定和材质——现有单采样前序命令流已接入

将着色输入契约映射为 root signature、PSO 和绑定布局；确定 DX12 编译器、
字节码和反射验证，不能假设更换编译器保持同样的点积舍入。
先生成纹理三角形，再真实独立材质，再多材质状态切换和单采样前序命令流。
缓存 PSO／root signature；需要的新管线预热不阻塞日常播放。

通过条件：同一 CPU 快照的 DX11／DX12 像素逐项验证；与 DX9 的结果单独记录。
单采样完全通过后才纳入已有 51 次绘制和多帧场景。

### Q4：多通道、屏障与 MSAA

编译颜色／深度附件和采样读写为资源状态转换，包括自阴影写后采样、
复制／回读、MSAA resolve 和 PRESENT。
最初保持单 graphics queue；不通过每次 draw 等待整台 GPU 来掩盖缺失依赖。

通过条件：多目标、自阴影、透明历史、resolve 和深度／模板控制测试通过；
debug layer／GPU validation 无相关资源状态或生命周期错误。

### Q5：应用接入、恢复和持续测试——达到 C

接同一个 FrameRenderData 和 Renderer 接口，逐步完成 P4/P5 的同一功能矩阵。
验证多个在途帧下的编辑、跳帧、录制、资源卸载和缩放。
设备移除／显式替换后重建 queue、fence、descriptor heaps 和 CPU 资源上传，
不把旧设备 fence 当新设备进度。

通过条件：同一运行脚本覆盖 DX9／DX11／DX12；x64/x86 的支持目标明确，
驱动／debug／GPU 测试证据完整；比较正确性、CPU 提交成本、GPU 帧耗时及内存。
DX12 不承诺天然更快；先用数据证明实际瓶颈和结果。

## 6. MME 是独立的效果兼容工程——达到 D

当前 MME 直接使用 IDirect3DDevice9、ID3DXEffect、D3DXHANDLE、DX9 纹理和技术通道。
仅给 RHI 增加 DX11/DX12 不能让这些效果自动运行。

建议顺序：先盘点内置效果与常用 FX 的语法／语义，再定义效果参数、技术／通道、
目标和纹理读写的后端无关描述；实现编译、绑定和通道执行；逐效果验证。
背景、阴影、动画纹理、离屏效果和多通道效果分别纳入支持表。
明确支持的语法与 DX9 固定功能依赖，无法转换的效果保留 DX9 路径和可诊断原因。

不默认采用 DX9 与 DX11/DX12 按绘制混合：只交换最终颜色无法保留深度、模板和
多目标效果历史。若未来需要跨 API 互操作，另做明确定义的通道边界和资源共享项目。
“所有现存第三方 MME 效果都原样兼容”在盘点前无法给出可靠工期和完成保证。

## 7. 工作量与顺序判断

以下为**单名熟悉该项目的开发者、有稳定 GPU 测试环境时的规划占位**，单位是开发人周，
包括实现与验证，不是日历承诺，也不是按代码行数估计的完成率。
在 P0、P1 做完后依据真实修改量和多帧结果重新估计；阻断项不能拿平均值掩盖。

| 交付 | 规划量级 | 条件与主要不确定性 |
| --- | --- | --- |
| A：受限单采样 DX11 应用预览 | 约 4–8 人周 | P0/P1/P2 与 P4 的已支持子集；不包含全部绘制或 MME |
| B：DX11 原生功能覆盖 | 从现在累计约 10–20 人周 | 完整通道、输出、测试；MSAA 精确一致是高风险验收，可能超出区间 |
| C：DX12 达到同一范围 | 在共享边界成熟后追加约 10–18 人周 | 队列／fence／资源和描述符正确性；不是 DX11 代码的机械翻译 |
| B + C | 从现在累计约 20–38 人周 | 允许 P6 并行；假设没有未预见的效果和驱动阻断 |
| D：任意第三方 MME 兼容 | 暂不估计 | 必须先得到语法／效果／多目标功能盘点及明确范围 |

多 GPU、8× MSAA 的严格零差异可能使 B/C 不能按原要求达到；此时报告具体受限能力，
由用户决定将“通用后端可用”与“原生 DX9 精确兼容”怎样作为产品档位。
本计划不提前变更现有零差异要求。

`P0 台账 → P1 常驻资源 → P2 实时生产者 → P3 通道 → P4 DX11 应用预览`
