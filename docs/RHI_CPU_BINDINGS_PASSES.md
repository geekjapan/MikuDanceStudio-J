# 独立预览：最终骨骼绑定与 CPU 场景通道

2026-10-19。在共享 CPU 世界之后，独立预览增加相机、饰品绑定查询，以及默认关闭的
`--scene-passes`。原编辑器的默认 DX9 路径保持原状。

## 职责

沿用 Unity 调研得到的职责边界，未复制 Unity 的实现或接口：

```text
SceneSession：PMM 文档、轨道、编辑、保存
    ↓
RuntimeCpuScene：共享 Bullet 世界、原有 IK/物理时序、最终骨骼与蒙皮
    ↓
RuntimeCpuSceneProducer：相机/灯光、CPU 饰品资源、通道与显示顺序
    ↓
CpuSceneFrameAssembler：原子组帧、跨帧资源身份和版本
    ↓
SceneRenderer：上传、复用、提交、设备更换后的恢复
    ↓
后端工厂 / 预览控制器 / DX11 或 DX12
```

正常帧不读取 DX9 几何、纹理或 GPU 状态。相机与饰品查询发生在现有 CPU 求解之后；
窗口缩放、组帧及设备替换均不推进 CPU 世界。

## 绑定

`BoneAttachment(model, bone)` 返回 `T(rest position) * final skin`。它支持仅骨骼模型，
并直接使用已完成 IK/物理的矩阵。无效模型、骨骼或非有限结果不会覆盖调用者的输出。

`AccessoryPlacement(slot)` 按原始次序组合缩放、Z/X/Y 旋转、位置、骨骼静止位置、最终蒙皮矩阵。
保留最后两次独立乘法，避免重新括号化引入额外舍入差异。相机通过同一最终骨骼查询得到跟随点；
需要旋转跟随时使用最终矩阵的旋转部分。v1 相机父级从可选尾部的关键帧索引映射取得。

求解按 `previousDisplayOrder`，绘制按 `selection.comboIndex`。显示索引相同时，遵循原循环
选取最小槽位；255 不参加绘制。饰品也按显示顺序选取槽位，并按 PMM 的前后分界绘制。

## 饰品导入和通道

资源解析器新增独立的饰品重选映射，复用模型的路径解码、场景相对目录和搜索根目录。
Win32 文件选择框只需提供重选路径。

Windows `.x` 导入使用 D3DX 文件数据解析器；它不创建 `ID3DXMesh` 或 DX9 设备。
当前支持单个静态 Mesh、三角形、显式法线、UV、材质及文件纹理。
位置与法线索引按需拆点，按材质建立索引范围；纹理由共同解码和显式 BoxLinear Mip 流程准备。
文件引用和解码字节属于 CPU 导入层，上传与释放仍由 `SceneRenderer` 负责。

原生对照发现，即使没有 Frame 节点，D3DX Mesh 导入仍会应用单位矩阵：位置经过
`D3DXVec3TransformCoord`，显式法线经过归一化。单位矩阵下的倒数舍入也能改变 1 ULP。
轴向和非单位法线均逐字节对照；先乘单位逆矩阵再归一化的候选被独立法线用例排除。
CPU 导入复用这两项 D3DX 数学操作，未采用按像素或按数值偏移的补丁。

`--scene-passes` 的顺序是：

1. 地面线与透明地面深度面。
2. 模型之前的饰品材质。
3. PMD 模型地面投影阴影。
4. 模型材质。
5. PMD 描边。
6. 模型之后的饰品材质。

任何不支持的操作会阻断整帧，调用者上一次的有效命令流保持不变。
资源路径变更要求重新导入，不能继续借用旧文件内容。

## 使用与验证

```powershell
mds_rhi_preview.exe dx11 scene.pmm --scene-passes
mds_rhi_preview.exe dx12 scene.pmm --scene-passes --reselect-accessory 0 accessory.x
MikuDanceStudio.exe --rhi-preview dx11 scene.pmm --scene-passes
```

`runtime_cpu_scene` 在原生参考调度的每个检查点额外逐字节比较最终骨骼绑定矩阵。
`runtime_cpu_bindings` 使用原创生成素材，检查绑定、显示与透明度、编辑保存回读、原子失败、
资源版本复用，以及显示顺序不同于求解顺序。上述测试不创建设备。

`runtime_cpu_x_native` 是独立的 GPU 验收：与原生 D3DX 导入逐三角形比较位置、法线、UV 和材质，
不把顶点拆分方式或缓冲布局当成格式契约。`rhi_independent_*` 运行 14 种输入，覆盖六帧跳帧、
播放、编辑、保存回读、缩放、最小化恢复、设备替换和卸载；恢复图像要求逐字节相等。

真实 PMM 的应用诊断仍分别记录 CPU 字段与 DX9/DX11/DX12 图像验收。
它验证原编辑器实际时间步下的结果，不能自动证明独立宿主另一组物理时间步与 UI 图像相同。
本轮日志和结果索引：`exports/cpu-bindings-passes-acceptance.json`。

## 本轮实测结果与未关闭项

Windows x64/x86 各一轮 16 项 CTest 通过，包括两个后端的硬件/WARP、14 种输入及原生 `.x`
几何对照。格式专用构建的 3 项资源解析/场景回读测试通过。
原生调度对照每轮覆盖 188 个检查点，并逐字节检查最终骨骼绑定矩阵。

两次初始真实 PMM v1/v2 审计各通过 9 个实时检查点、1145 项完整场景检查。
随后对最终 x64 应用的追加复跑，在 v1 `seek5` 第 23 次绘制出现两个后端各 7 个像素差异，
颜色通道相差 1，字段对照通过；原生/候选图、逐像素 CSV 与失败报告已保留。
因此当前真实完整场景图像验收仍被阻断，不能用之前成功的一轮覆盖这次失败。

x86 CPU 场景测试追加复跑出现访问冲突（0xC0000005），日志在绑定 v1 场景之前中断。
直接运行 6 次、补充异常栈记录后 CTest 连续 8 次及随后复验均通过，尚未取得异常栈或定位根因。
测试已保留逐检查点输出及异常栈记录能力；这项稳定性问题仍开放。

抽查原版配套的 `negi.x`、`mic.x`、`stage01.x`、`nekomimi.x`，两个架构均因非三角形面而明确拒绝。
这些真实饰品未通过新导入器验收。下一项饰品工作是多边形三角化及原生逐三角形/图像对照。

## 尚未开放

此开关是独立预览的受控范围，未替换主窗口渲染器。
Frame/多 Mesh、无显式法线、多边形 `.x`、VAC、动态屏幕纹理、饰品投影阴影、PMX 边缘通道、
自阴影目标、背景与 MME 仍会阻断对应完整场景。默认不启用后端 measured 兼容策略。
单独的 CPU 组帧与设备恢复测试通过，也不代表新的完整场景已经取得真实 DX9 零像素验收。

CPU 调度、格式、资源解析与 RHI 契约可移植；原生模型记录、D3DX CPU 数学及本次 `.x` 文件解析
仍是 Windows 适配边界，不能据此声称 Linux/macOS 已运行完整模型求解和饰品导入。
